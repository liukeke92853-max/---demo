本次新增 / 改造

已确认：新增推广位由“保存立即生效”改为“发起邀请 → 被邀机构在小程序接受 → 合作生效”。一级、二级均由顶层渠道发起配置；一级邀请方为渠道，二级邀请方展示所配置的直接上级。后台操作人与业务邀请方分别留痕。

本次改造：推广位列表沿截图原列结构，新增“合作状态”，取值为待接受、合作中、已关闭；“已拒绝”为待确认建议分支。顶部筛选区新增“合作状态”下拉单选，不提供列表上方快捷标签；默认全部，与当前日期、推广位搜索、等级条件取交集；输入框按名称或ID实时筛选，等级和日期变化即时筛选，日期起晚于止时提示且列表为空。既有筛选不标为新增。

接受邀请（新增）

目标机构查看邀请方、拟合作层级与提成配置，点击“接受邀请”后后端核验当前登录机构、处理权限、邀请仍待接受、渠道合作有效、上级有效、比例快照无冲突及机构占用。成功后该批次转合作中、记录接受人及时间；重复点击或多端并发仅生效一次。越权或状态变化时不生效，提示并刷新。机构内谁可接受、是否需要二次确认待确认；Demo以目标机构本人点击即接受演示。邀请展示条款与拒绝能力为评审建议。

关闭推广位弹窗（新增）

结构 / 字段规则与默认值
关闭对象只读：机构名称、ID、推广位层级、合作批次；无可编辑字段。
继承说明只读：顶层渠道、受影响生效中邀约的数量和明细；明确不可再次启用，后续需重新邀请。Demo只转演示生效中邀约，正式继承状态范围待确认。
存在下属二级展示下属合作中二级数量、名单与全部受影响邀约；确认后一级和这些二级一起关闭，全部邀约归顶层渠道。存在待接受二级时，其处理规则待确认，本版暂阻止该场景关闭。
取消 / 确认关闭取消无变化；无待接受二级的未决场景时允许演示关闭。提交前重查状态和归属，成功后关闭记录转终态、受影响当前关系归渠道并写明细日志；失败时不允许部分迁移或只关闭无继承。
关闭反馈成功提示继承条数，列表与日志同步更新；后台须支持幂等和事务处理。关闭原因、审批与通知未确认为本期需求，不新增必填项。

日志入口（新增）

逐行“日志”定位该合作批次，下方核对区展开后显示操作时间（北京时间，精确到秒）、操作人、动作、机构、批次及前后变化。继承事件记录原归属、顶层目标渠道与逐条邀约标识；点击“查看全部日志”恢复全量。日志只读，Demo重置仅清空本地模拟数据。

前后状态流转

一级：渠道输入机构 → 渠道名义邀请 → 待接受 → 目标机构接受 → 一级合作中。

二级：渠道选择一级上级并输入机构 → 所选一级名义邀请 → 待接受 → 目标机构接受 → 二级合作中。

关闭：合作中 → 确认关闭 → 该批次已关闭 + 当前邀约归顶层渠道 + 原始来源与继承日志留存。重新邀请 → 新待接受批次 → 再次接受 → 新合作生效，旧关闭批次不变。

待接受前拒绝（建议）：邀请已拒绝，不建立有效推广位关系，保留处理记录；可重新发邀请。邀请有效期、撤回、过期、催办和通知失败重试等需另行确认，Demo不设自动同意或超时生效。

待确认边界与研发影响

需优先确认：
  1. 一级名下待接受二级邀请如何处理；合作中二级已确认随一级一起关闭，全部邀约归顶层渠道。
  2. 已确认关闭前订单及待结算收益保留原归属，关闭后新订单归顶层渠道；新旧订单的技术判定字段、延迟同步与重算如何按关闭时刻匹配仍待确认。Demo不计算或迁移订单。
  3. 继承是否包含待生效、即将失效邀约；已失效记录是否仅存历史；保护期限是否沿用，渠道已有同机构关系时如何去重。
  4. 机构中谁有权接受，消息发给哪些账号，使用站内消息还是微信订阅通知，模板与实际接入方式。
  5. 邀请有效期、拒绝、撤回、配置变更后二次确认、跨渠道机构排他范围；重新合作是否迁回旧邀约。

研发建议，非现有接口事实：建立邀请快照、接受结果与不可逆关闭事件；当前有效关系与历史批次分离。发送、接受、关闭均做身份和渠道归属校验；并发接受、并发关闭及新邀约写入须通过事务 / 锁或等效机制保证一次性。通知与合作生效分开记录，消息投递成功不代表接受成功。

继承不能只改推广位状态或覆盖全部历史外键；须核对邀约记录、授权申请中的渠道 / 推广位关联、账号统计、订单生成、结算任务、筛选权限及旧邀约链接拦截。顶层渠道已终止时的处置不能直接沿用本次继承规则；原渠道整体停用逻辑单独评估。技术表结构、接口路径及索引迁移由研发评审，不虚构已存在字段。
